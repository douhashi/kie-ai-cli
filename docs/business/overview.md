# kie-ai-cli コンセプト

kie.ai の非公式 CLI。何を作るのか、なぜその形なのかを定める。

## 何を作るか

kie.ai の生成 API を端末から使うためのコマンドラインツール。
Go による単一バイナリで配布し、追加のランタイムを要求しない。

## なぜ必要か

kie.ai の API は非同期のタスク型で、タスクを作成し、taskId で照会し、
結果 URL を受け取る、という 3 往復を要する。1 リクエストごとに完了を待つと、
複数の生成を並行して回せない。

さらに kie.ai には**タスク一覧を返すエンドポイントが存在しない**。
照会は常に taskId 単位であり、投げたタスクを覚えるのはクライアント側の責務になる。

したがってこの CLI の核は「待たずに投げ、後からまとめて回収する」ことであり、
そのためにローカルの台帳を持つ。curl との差はここにある。

## 中核の設計判断

### 標準 API と Market を区別しない

kie.ai には Market の統一エンドポイント（作成と照会が 1 組）と、Suno・Veo3・
4o Image・Flux Kontext・Runway・File Upload の標準 API がある。両者の差は
kie.ai 側の歴史的経緯であり、利用者にとって意味を持たない。

CLI は **作成と照会の 1 組を「モデル」** として同格に並べ、系統差は内部で吸収する。
Suno の WAV 変換のように既存の taskId を入力に取る後段処理も、同じモデルとして扱う。

モデル ID は Market が `model` 値（例: `bytedance/seedream-v4-text-to-image`）、
標準 API が docs のパス由来（例: `suno-api/generate-music`）とする。後者は kie.ai が
保証しない、こちら側の命名規約である。

### コマンドは名詞と動詞の 2 階層で並べる

打ち手は人間である。231 件を端末から探して投入するため、`--json` は補助に留め、
既定の出力は読める形にする。

名詞は `model` / `task` / `catalog` / `config` / `file` / `credits` の 6 つ。
境界は「**kie.ai 側にあるものが `model`、自分が投げたものが `task`**」で引く。
語数が増えても例外を作らない。動詞が 1 つしかない `credits show` も 2 階層に揃える。

モデル ID は `task run` の位置引数で受け、短縮も別名も設けない。231 件の候補を
部分一致で解決すると、カタログ更新で昨日通った呼び出しが今日は曖昧になる。
代わりにシェル補完を唯一の入力補助とし、補完用の ID 一覧を別に持つ。

`--json` は成功時の出力形式のみを変える。エラーは種類を問わず stderr へ平文で出し、
終了コードで区別する。`gh` と `kubectl` がいずれもこの分担を採っている。エラーを
stdout の JSON にすると成功時のスキーマと混ざり、パイプの先が静かに壊れる。

### カタログを docs から生成する

英語版だけで 231 本の API ページがあり、Market のモデルは入れ替わりが速い。
手書きの定義では追従できない。

`docs.kie.ai/llms.txt` が全ページを列挙し、各ページに OpenAPI 3.0 が埋め込まれている。
これを巡回してカタログを生成し、CI で定期実行して差分を PR として出す。
入力の正しさは Go の型ではなく、生成器側のテストで担保する。

main に入ったカタログは tag `catalog` の Release 資産として公開する。取得側が知る
URL は 1 本だけで、版を刻まない。**公開時刻は資産の `updated_at` が持ち、
`catalog.json` の中には入れない。** 中に時刻を入れると、内容が同じ日にも差分が出て
毎日 PR が立つ。公開物はコミット済みと byte 一致させ、再生成して上げ直さない。

絞り込みの軸も `llms.txt` から取る。各行が `Image    Models > Seedream` という
系統とベンダーの 2 階層を持つ。手書きの分類は要らない。

ただし**軸の値は正規化する**。`--category image` と小文字語で確定している以上、
パンくずをそのまま採ることはできない。第 1 階層の末尾 ` Models` を落として
小文字にするのを基本とし、この形を外れる `Suno API`（→ `music`）と
`Veo3.1 API`（→ `video`）の 2 件だけを別名表で寄せる。kie.ai 自身が
`Video Models > Runway API` や `Image Models > 4o Image API` という形を採り、
`Music Models` も実在する。2 件はその規約の適用漏れであり、こちらで分類を
新設しているのではない。**別名表にも派生規則にも当てはまらないパンくずが
現れたら生成を失敗させる。** 黙って通せば、表が古くなったことに誰も気づかない。

1 行の説明はページ側の OpenAPI から採る。`llms.txt` の説明はページ冒頭行の
写しにすぎず、半数以上が `## Create Task` のような見出しの断片である。

**taskId を返さないエンドポイントはカタログに載せない。** Chat Models 35 本は
`/v1/chat/completions` の同期 API で、台帳に載る行を持たない。判定は系統名ではなく
応答の形で行い、Market に同期モデルが増えても取りこぼさないようにする。

### カタログはバイナリに焼き込む

実行時に取りに行くと、初回とネットワーク障害時に何も動かない。
生成したカタログはビルド時にバイナリへ埋め込み、明示コマンドでのみ上書きする。
自動更新は行わない。カタログの鮮度のために投入が遅れるのは本末転倒だからである。

鮮度はネットワーク無しでは判定できないため、生成日からの経過を目安に警告する。

### 完了確認と保存を分ける

完了確認は結果 URL を台帳に記録して返すのみとし、保存は別コマンドで行う。
生成物には失効があり（4o Image は 14 日、ダウンロード URL は 20 分）、
取りこぼしは「未保存の一覧が出せる」ことで塞ぐ。

照会そのものも一覧から分ける。照会は taskId 単位でしか行えず、未完了が N 件あれば
N 回叩くことになる。一覧のたびに照会すると、件数が増えるほど一覧が使えなくなる。

ダウンロード URL の再発行は保存の内部処理とし、コマンドにしない。20 分で失効する
URL を利用者が手に持つ意味がない。

### 状態はすべて 1 か所に置く

台帳・カタログ・設定は `$XDG_DATA_HOME/kie-ai-cli` 配下に集約する。
台帳は SQLite とし、未保存の絞り込みと状態更新に耐えさせる。
スキーマ移行は初期実装に含める。移行が無ければ、更新のたびに台帳を捨てさせることになる。

API キーは環境変数を優先し、無ければ設定ファイルから読む。設定ファイルは 0600 で作る。

## 制約・前提

- kie.ai の照会は taskId 単位のみで、タスク一覧を返すエンドポイントは無い
- 英語版だけで 231 本の API ページがあり、各ページに OpenAPI 3.0 が埋め込まれている
- Chat Models 35 本は同期 API で taskId を返さないため、対象外とする
- File Upload 3 本は同期 API で、URL・ストリーム・Base64 の入力形式違いにすぎない
- 4o Image の生成物は 14 日、ダウンロード URL は 20 分で失効する
- README を含め、外部に見えるインターフェースはすべて英語で記述する
- 本プロジェクトは非公式であり、kie.ai の仕様変更に対する保証を持たない
