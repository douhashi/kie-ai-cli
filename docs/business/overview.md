# kie-ai-cli コンセプト

kie.ai の非公式 CLI。何を作るのか、なぜその形なのかを定める。

## 何を作るか

kie.ai の生成 API を端末から使うためのコマンドラインツール。
Go による単一バイナリで配布し、追加のランタイムを要求しない。

## なぜ必要か

kie.ai の API は非同期のタスク型で、タスクを作成し、taskId で照会し、
結果 URL を受け取る、という 3 往復を要する。1 リクエストごとに完了を待つと、
複数の生成を並行して回せない。

さらに kie.ai には**タスク一覧を返すエンドポイントが存在しない**。
照会は常に taskId 単位であり、投げたタスクを覚えるのはクライアント側の責務になる。

したがってこの CLI の核は「待たずに投げ、後からまとめて回収する」ことであり、
そのためにローカルの台帳を持つ。curl との差はここにある。

## 中核の設計判断

### 標準 API と Market を区別しない

kie.ai には Market の統一エンドポイント（作成と照会が 1 組）と、Suno・Veo3・
4o Image・Flux Kontext・Runway・File Upload の標準 API がある。両者の差は
kie.ai 側の歴史的経緯であり、利用者にとって意味を持たない。

CLI は **作成と照会の 1 組を「操作」** として同格に並べ、系統差は内部で吸収する。
Suno の WAV 変換のように既存の taskId を入力に取る後段処理も、同じ「操作」として扱う。

操作 ID は Market が `model` 値（例: `google/nano-banana`）、標準 API が docs の
パス由来（例: `suno-api/generate`）とする。後者は kie.ai が保証しない、こちら側の命名規約である。

### 操作カタログを docs から生成する

英語版だけで 231 本の API ページがあり、Market のモデルは入れ替わりが速い。
手書きの定義では追従できない。

`docs.kie.ai/llms.txt` が全ページを列挙し、各ページに OpenAPI 3.0 が埋め込まれている。
これを巡回して操作カタログを生成し、CI で定期実行して差分を PR として出す。
入力の正しさは Go の型ではなく、生成器側のテストで担保する。

### カタログはバイナリに焼き込む

実行時に取りに行くと、初回とネットワーク障害時に何も動かない。
生成したカタログはビルド時にバイナリへ埋め込み、明示コマンドでのみ上書きする。
自動更新は行わない。カタログの鮮度のために投入が遅れるのは本末転倒だからである。

鮮度はネットワーク無しでは判定できないため、生成日からの経過を目安に警告する。

### 完了確認と保存を分ける

完了確認は結果 URL を台帳に記録して返すのみとし、保存は別コマンドで行う。
生成物には失効があり（4o Image は 14 日、ダウンロード URL は 20 分）、
取りこぼしは「未保存の一覧が出せる」ことで塞ぐ。

### 状態はすべて 1 か所に置く

台帳・カタログ・設定は `$XDG_DATA_HOME/kie-ai-cli` 配下に集約する。
台帳は SQLite とし、未保存の絞り込みと状態更新に耐えさせる。
スキーマ移行は初期実装に含める。移行が無ければ、更新のたびに台帳を捨てさせることになる。

API キーは環境変数を優先し、無ければ設定ファイルから読む。設定ファイルは 0600 で作る。

## 制約・前提

- kie.ai の照会は taskId 単位のみで、タスク一覧を返すエンドポイントは無い
- 英語版だけで 231 本の API ページがあり、各ページに OpenAPI 3.0 が埋め込まれている
- 4o Image の生成物は 14 日、ダウンロード URL は 20 分で失効する
- README を含め、外部に見えるインターフェースはすべて英語で記述する
- 本プロジェクトは非公式であり、kie.ai の仕様変更に対する保証を持たない
